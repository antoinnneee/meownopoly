  Synthèse de la lecture générale

  Le pivot en bref : la V3 transforme le jeu en substrat de gameplay créé par
  des IA clientes. Chaque joueur invoque « son IA » depuis un tchat ingame ;
  elle matérialise ses demandes en composant les briques existantes de l'éditeur
  et en y embarquant du JS. Une IA arbitre obligatoire chez l'hôte valide
  chaque proposition avant application. Le cadrage est très avancé : 39
  décisions (D1→D39) sont actées, 16 risques identifiés, et il ne reste que 6
  questions ouvertes (Q-E06, E08, J02, J04, J06, J08).

  Les briques logicielles à créer ou modifier (détail complet dans le suivi §3)
  :

  1. Passerelle MCP AiGatewayServer (M1) — serveur MCP streamable HTTP loopback
  embarqué dans le jeu, ~10 tools groupés, tokens distincts proposant/arbitre.
  Prérequis : installer QtHttpServer.
  2. Superviseur d'agents + tchat ingame (M2) — spawn/supervision de claude 
  -p/Codex via QProcess, handshake arbitre, UX lobby 4 états.
  3. Fiabilité applicative P2P (M3) — ACK/retry/dédup au-dessus de Catway
  (reliable.io ne retransmet pas — point corrigé par l'audit).
  4. Transactions atomiques (M4) — passer du groupement actuel à
  prepare/commit/rollback.
  5. Journal d'événements métier GameplayEventBus (M5) — curseur, audit,
  adaptateur pour l'IA.
  6. Espace mémoire config/state + bus d'état runtime (M6) — sur ItemSnapable,
  session et joueurs ; delta 30 Hz + snapshots + resync.
  7. Sauvegarde de partie distincte de la map (M7).
  8. Store d'artefacts par hash (M8) — refcount, GC au save.
  9. Sandbox à deux étages (M9, risque n°1 / prototype R1) — banc d'essai
  hors-process meow_testbench (spécifié doc 12) + confinement runtime in-process
  (façade Meow.GameApi, budgets D34).
  10. Enveloppe de proposition (doc 13) — cycle de vie, verdict à deux
  audiences, plancher d'arbitrage non contournable.
  11. Migration d'hôte V3 (M10), bibliothèque GLB (M11), skill générée au build
  (M12), qualification Linux (M13), et le moteur de règles (doc 06, le moins
  mûr).

  Prérequis bloquant signalé partout : assainir la sérialisation string-manuelle
  de ItemSnapable::toJSON (risque R4), qui conditionne le snapshot du banc
  d'essai.

● Reprenons depuis le début : de quoi je parle exactement

  Ce qu'est une « session » dans votre code aujourd'hui

  Catway, c'est le transport brut : des paquets UDP P2P entre pairs. Au-dessus,
  chaque domaine fonctionnel du jeu a sa propre « session », c'est-à-dire une
  classe C++ qui définit :

  - une plage de types de messages (le 1er octet du paquet) pour cohabiter sur
  le même transport : GameSession utilise 0x01–0x11, EditorSession 0x20+,
  PhysicsSession 0x40+ ;
  - un modèle d'autorité host-authoritative : les clients envoient des
  intentions, l'hôte valide/applique/rebroadcaste ;
  - un cycle de vie : démarrage (startAsHost/startAsClient), handshake d'entrée
  (Hello → full-sync de l'état), arrêt, et pour l'éditeur la migration d'hôte
  (élection, promotion, resync).

  COLLAB_SESSION_PATTERN.md (doc V2) décrit justement ce moule pour pouvoir en
  créer d'autres.

  Ce que la V3 doit transporter de nouveau

  Le pipeline de proposition (docs 11/13) génère de nouveaux flux réseau,
  uniquement en mode collab et runtime (en solo tout est local, aucun réseau) :

  1. client → hôte : l'enveloppe de proposition (intention, opérations, source
  QML/JS jusqu'à 20 KB) — avec garanties « commit » (ACK applicatif, retry,
  dédup, chantier M3) ;
  2. hôte → auteur : le verdict (accepté/amendé/rejeté + raisons) ;
  3. hôte → tous : l'application des effets validés + l'entrée de journal
  répliquée ;
  4. plus tard : le bus d'état mémoire (deltas 30 Hz, snapshots — D35) et le
  checkpoint de migration (D37).

  La question 2, c'est : dans quelle « boîte » réseau ces messages vivent-ils ?

  Option 1 — Nouvelle session dédiée (ex. ProposalSession)

  On crée une paire classe/protocole neuve sur le moule existant, avec sa propre
  plage (ex. 0x60+).

  Ce que ça implique concrètement :
  - Plus de travail initial : nouvelle classe C++, son protocole, son handshake,
  son câblage dans main.qml, et il faudra étendre la migration d'hôte pour
  qu'elle couvre deux sessions (l'éditeur + celle-ci) de façon coordonnée (le
  checkpoint D37 devra de toute façon orchestrer ça).
  - En échange : l'arbitrage est indépendant de l'éditeur. Quand vous livrerez
  le 3e mode (partie runtime co-construite, D23), il n'y a pas d'éditeur ouvert
  — la session de proposition tourne telle quelle à côté de
  GameSession/PhysicsSession. Rien à re-migrer. Et zéro risque de casser le
  collab éditeur V2 qui marche aujourd'hui.

  Option 2 — Étendre EditorSession

  On ajoute les types Proposal, Verdict, etc. à la plage 0x20+ existante et les
  handlers dans EditorSession.

  Ce que ça implique concrètement :
  - Beaucoup moins de code maintenant : le cycle Hello/FullSync/migration existe
  déjà, on greffe dessus. Le slice collab éditeur arrive plus vite.
  - Mais : le jour du mode runtime, soit vous faites tourner une EditorSession
  sans éditeur (conceptuellement bancal : son full-sync, son undo, ses ops n'ont
  pas de sens en partie), soit vous extrayez à ce moment-là les messages de
  proposition vers une session dédiée — c'est-à-dire l'option 1, mais payée plus
  tard, avec un protocole déjà en circulation à migrer. Ça couple aussi la
  pièce de gouvernance centrale du pivot au module éditeur.

  Option 3 — Différer

  On écrit les deux options dans le doc 01 §2.5 et on tranche à l'ouverture des
  chantiers. C'est sans coût pour le vertical slice (solo = pas de réseau du
  tout). Le risque est ailleurs : le doc 13 (enveloppe) et le doc 10 (M3)
  parlent déjà de « transport commit », et si on commence M1/M3 sans avoir
  choisi la boîte, on risque de figer des détails de protocole au mauvais
  endroit.

  En une phrase

  C'est un choix entre payer maintenant une session propre qui servira aux trois
  modes (option 1), aller plus vite sur l'éditeur en acceptant une dette à 
  rembourser au mode runtime (option 2), ou repousser le choix puisque le slice
  solo n'en dépend pas (option 3). Ma recommandation reste l'option 1, mais
  l'option 3 est défendable si vous voulez garder la décision pour le moment où
  vous aurez le slice solo sous les yeux.

  Laquelle retenez-vous ?

  Question 3 en détail — où s'exécute le préfiltre mécanique P0

  Ce qu'est P0. Dans le pipeline de validation (doc 12 §1 et §3), P0 est la
  toute première barrière, purement mécanique et quasi gratuite : parser le
  QML/JS, vérifier l'allow-list d'imports (D34), la taille ≤ 20 KB, et calculer
  le requestType de l'enveloppe (data_safe/structure/rules/code — doc 13). Elle
  rejette immédiatement les cas triviaux (ex. import QtWebSockets) sans payer ni
  l'arbitre LLM ni le spawn du banc d'essai. Le doc 12 dit qu'elle tourne «
  dans le jeu » — mais en collab, « le jeu » tourne chez chaque pair, et les
  docs ne précisent pas chez qui : le schéma du doc 01 §1 la place chez l'hôte,
  après le transport de l'enveloppe.

  Pourquoi ça compte. Deux propriétés sont en tension :

  - L'autorité. Le calcul du requestType par P0 est ce qui rend le plancher
  d'arbitrage D25 non contournable (une enveloppe contenant du code est code,
  quoi qu'en dise l'IA). Si l'hôte fait confiance à un P0 exécuté chez un

  traverse toutes les couches de l'architecture au moins une fois, de bout en

  opposition à construire chaque couche à fond l'une après l'autre.

  passerelle MCP, adaptateur agents/tchat, skill, enveloppe, arbitre, banc,

  Le problème : un artefact qui dépend d'un module

  Définition courte préalable — dépendance d'artefact : une capacité que le code
  généré appelle via la façade (stats.addModifier, session.get…) mais dont la
  disponibilité dépend de l'état de la map (module activé ou non), pas du code
  lui-même.

  Concrètement : l'IA propose une plaque qui fait stats.addModifier(...). Si le
  module stats n'est pas activé sur cette map, que se passe-t-il ? Aujourd'hui
  les docs ne le disent pas, et les trois issues possibles par défaut sont
  toutes mauvaises :
  - Échec silencieux au runtime : l'artefact passe le banc, s'applique, et ne
  fait rien en partie — le pire cas (le joueur voit un item mort).
  - Activation implicite : appeler la façade active le module à la volée — effet
  de bord caché que l'arbitre n'a jamais jugé.
  - Rejet sec sans explication : l'IA ne peut pas converger (contraire à S3).

  Et remarquez que votre vertical slice est déjà concerné : la plaque piégée du
  fil rouge utilise stats.addModifier — elle suppose le module stats actif.

  Le mécanisme que je propose (3 morceaux)

  1. Dépendances déclarées dans l'enveloppe. Le bloc artifacts[] du doc 13 porte
  déjà declaredWriteSet (les clés que l'artefact écrira) et listensTo (les
  événements qu'il écoute). On ajoute un champ frère : requiresModules: 
  ["stats"] — déclaré par l'IA, vérifié mécaniquement : en P0 contre l'état réel
  de la map (module absent → rejet immédiat, avant l'arbitre), et au banc (le
  snapshot du job doit inclure l'état des modules, ce qui manque d'ailleurs au
  schéma du job doc 12 §2.3).

  2. Erreur actionnable. Le rejet est {code: "missing_module", details: "le 
  module 'stats' n'est pas actif sur cette map", retryable: true} — l'IA sait
  exactement quoi corriger (S3).

  3. Comment l'IA satisfait la dépendance — c'est là que votre question rejoint
  la question 4, avec deux variantes :
  - Variante A (= option 2 renforcée) : le tool module_config entre au manifeste
  MVP. L'IA peut alors inclure l'activation du module dans la même enveloppe
  que l'artefact — lot atomique (« tout-ou-rien », D14 : soit toutes les
  opérations de l'enveloppe s'appliquent, soit aucune). L'arbitre juge le tout
  d'un bloc (« cette proposition active le module stats ET pose la plaque »).
  L'activation serait de requestType: structure. Le slice l'exercerait
  naturellement (S1 activerait stats).

  Revue du doc 02 — 02_CANAL_IA.md

  Définitions courtes des concepts du doc

  - MCP (Model Context Protocol) : protocole standard par lequel un agent LLM
  découvre et appelle des tools (fonctions typées) exposés par un serveur ;
  claude -p et Codex le parlent nativement.
  - Streamable HTTP : l'un des transports MCP — le serveur est un endpoint HTTP
  ; le client POSTe des requêtes JSON-RPC 2.0 (format requête/réponse JSON
  corrélé par id ; 3 méthodes suffisent : initialize, tools/list, tools/call).
  - Loopback : interface réseau 127.0.0.1 — joignable uniquement depuis la
  machine elle-même.
  - Bearer token : secret passé dans l'en-tête HTTP de chaque requête ; ici
  généré par session et injecté au spawn de l'agent, il bloque les autres 
  process de la machine (risque R3).
  - Prompt caching : les fournisseurs LLM facturent moins cher un préfixe de
  prompt identique d'une requête à l'autre — d'où l'exigence « pré-prompt skill
  + schémas de tools stables ».
  - Journal métier / curseur : le journal (M5/D19) est la suite numérotée (seq
  monotone) des événements de la partie ; un curseur est la position seq
  jusqu'où un lecteur a consommé — events_poll(cursor) rend « tout ce qui s'est
  passé depuis ».

  Résumé bloc par bloc

  §1 — Rôle. Le canal est l'unique point de contact IA↔jeu, et son but est de
  créer des briques de gameplay porteuses de logique — pas de tester le jeu.
  Frontière non négociable : l'IA ne parle jamais à l'automation (port 7700) ;
  le canal ré-expose un sous-ensemble curé.

  §2 / §2 bis — Pourquoi MCP, et sous quelle forme (D20/D21). Le WS maison est
  mort car l'app spawne elle-même les agents (D10) : découverte et
  authentification sont résolues par construction, et les deux CLIs parlent MCP
  nativement. Forme : endpoint streamable HTTP loopback dans le process du jeu
  (sous-ensemble JSON-RPC à implémenter en C++, QtHttpServer à installer, repli
  pont stdio documenté).

  §3 — Économie de tokens (contrainte de conception). La skill porte la
  connaissance (cachée), le catalogue reste réduit et groupé (tools paramétrés),
  résultats compacts/paginés, préfixe stable, help(topic) en divulgation
  progressive.

  §4 — Événements. Pas d'agent persistant : résumé des événements injecté à 
  chaque invocation + events_poll(cursor) pour se resynchroniser en cours de
  tâche. Nécessite l'adaptateur d'événements unifié (= brique §2.8/M5 qu'on a
  promue au doc 01).

  §5 — Catalogue. 5.1 : les 13 hooks existants (vérifiés ce jour) réutilisés
  comme implémentation. 5.2 : les vrais chantiers — introspection d'état
  (listTiles/getTile), édition par uuid, mémoire, enums, roster, runtime
  (totalement absent en V2), qml.instantiate, events_poll, screenshot (D22).

  §6 — Boucle perception→action : contexte → observe → décide → agit → vérifie ;
  exigence : erreurs de tools exploitables par une IA (code stable, retryable).

  §7 — Sécurité : loopback strict opt-in, token au spawn, deux identités chez
  l'hôte, allow-list de tools, le QML transite en enveloppe, quotas, garanties
  applicatives P2P.

❯ §1 — Je comprend l'idée. Quels sont globalement les problématiques si l'on    
  expose la sandbox de test d'un item, sa génération, à l'ia cliente ? Afin que 
  cette dernière puissent suivre voir modifier en "temps-réel" l'évolution et   
  la perfection d'un item avant sa pose au jeu en runtime. Cela implique de     
  modifier le cadrage mais quelle est la portée que tu estimerais               

● Excellente piste — analysons-la proprement. Définition courte de ce que vous
  décrivez : un mode atelier (ou dry-run) — la possibilité pour l'IA cliente
  d'exécuter le banc d'essai comme outil d'itération pendant la création, avant
  artifact_submit, au lieu de ne le rencontrer qu'en aval comme couperet de
  validation.

  Ce que ça ne casse pas (bonne nouvelle)

  Le pipeline autoritaire reste intact : le banc-verdict (après arbitre,
  D26/D32) ne bouge pas. Un dry-run ne serait jamais un laissez-passer —
  l'artefact soumis repasse toujours P0 → arbitre → banc autoritaire. On aurait
  donc deux usages du même exécutable meow_testbench : atelier (avant
  soumission, au service de l'IA) et verdict (après arbitre, au service de
  l'hôte). C'est exactement le même patron que ce qu'on vient d'acter pour P0
  (copie locale fail-fast + exécution autoritaire chez l'hôte).

  Et le bénéfice est réel : l'IA converge avant de soumettre → moins
  d'allers-retours d'arbitrage (chaque rejet S3 coûte un appel LLM arbitre +
  potentiellement un run de banc), meilleure UX, et le critère « ≤ 2 itérations
  » de S3 devient facile.

  Les problématiques, par ordre de gravité

  1. Ressources (la vraie contrainte). Un run de banc = un process Qt offscreen,
  cible < 8 s par validation saine. Une IA qui « perfectionne » peut itérer
  10-20 fois. En solo, c'est la machine du joueur — acceptable. En collab, il ne
  faut surtout pas que les dry-runs des clients tournent chez l'hôte (déni de
  service trivial) : le dry-run doit être local chez l'auteur (le binaire du
  banc est livré avec chaque installation). Il faut un quota de dry-runs par
  invocation (pattern #define, ex. 10).
  2. Le « temps réel » est le point cher. Le banc actuel est batch : un job JSON
  entre, un verdict JSON sort, le process meurt. « Suivre et modifier en temps
  réel » impliquerait un mode session : process qui reste vivant, l'IA pousse
  une version modifiée, déclenche des stimuli à la demande, lit des métriques en
  continu — un nouveau protocole jeu↔banc, un cycle de vie de session lié à
  l'invocation, et si vous voulez du visuel, il faudrait sortir du headless (le
  banc est -platform offscreen, il ne rend rien) — gros surcoût. À noter : le
  mode pool prévu (doc 12 §6, jobs par stdin sur process chaud) fournit déjà 80
  % de la plomberie d'un mode itératif sans aller jusqu'au streaming.
  3. Divergence de verdicts. Un dry-run pass chez l'auteur peut donner fail chez
  l'hôte (versions de banc/budgets différentes entre installations). Mitigeable
  : benchVersion + budgets sont déjà dans le job et la clé de cache — l'erreur
  devient explicable. Mais la skill doit marteler : un pass local n'est pas une 
  acceptation.
  4. Sécurité : quasi neutre. Le banc est déjà conçu pour exécuter du code
  hostile (hors-process, masqué, sans module réseau lié). L'exposer à la
  proposante n'ajoute pas de surface — tant que le verdict qui fait foi reste
  celui de l'hôte, et que le cache de verdicts de l'hôte n'accepte jamais un
  verdict calculé par un pair (R16 : pas de signature au MVP).

  Portée estimée sur le cadrage : moyenne, en deux paliers

  - Palier 1 (petit, MVP possible) : un tool artifact_dryrun(source, 
  targetUuid?) — one-shot, local, renvoie le verdict complet avec les métriques
  (l'IA voit tickUsP95, writeSet observé, etc. — c'est déjà très « suivre la
  perfection de l'item »). Impact docs : 12e tool (Q-E08), un § dans doc 12
  (mode atelier + quota), une note doc 02 §5, une décision D42, skill
  (avertissement pass local ≠ acceptation). Réutilise le banc tel quel : ~zéro 
  architecture nouvelle.
  - Palier 2 (post-MVP) : la session atelier interactive (stimuli à la demande,
  métriques continues, éventuellement rendu/capture du banc). Nouveau protocole,
  cycle de vie, à cadrer plus tard — je le noterais comme extension dans doc 12
  §11.

  Ma recommandation : acter le palier 1 au MVP (il rentabilise le banc et sert
  directement S3) + tracer le palier 2 comme extension. Avec la règle stricte :
  dry-run local chez l'auteur, quota par invocation, jamais de confiance
  inter-pairs sur les verdicts.

  On acte ça (palier 1 MVP + palier 2 tracé) ? Ou vous préférez le palier 1
  lui-même en post-MVP pour ne pas grossir le slice ? Ensuite on reviendra à la
  question Q-E06 laissée en suspens.
